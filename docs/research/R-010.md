## Executive consensus

**KEEP_CONDITIONALLY:** retain persistent ONNX Runtime/VitisAIExecutionProvider,
unchanged fixed256 SESR-M7 INT8, host staging, separate CPU agreement and the
strict physical-proof gate. SteamOS on Ryzen AI Z2 Extreme remains the primary
acceptance tuple. No runtime/backend, model, scheduler or presentation integration
is replaced by this research. Exact3× ESPCN remains future production research.

AMD's1.8 Linux documentation directly describes a CNN quicktest that compiles and
runs on the NPU. This supports the existence of the Ubuntu reference path, not
SteamOS compatibility. R-010 reports a conflicting generic ORT support table;
that page could not be independently retrieved in this amendment. Preserve the
discrepancy as unrechecked documentation, not proof that Linux Vitis is absent.

The decisive result is still actual H1 execution under the owner's SteamOS tuple,
followed by complete-frame H2. The current H1 harness keeps candidates INCONCLUSIVE
until real placement/context formats and attribution are understood. No physical
gate, performance target or production-readiness claim advances here.

## Conditional alternatives and revisit conditions

1. IRON/MLIR-AIE+XRT: first low-level compute-proof fallback if Vitis fails;
   custom graph/kernel responsibility is substantial.
2. xdna-engine: SR-specific design reference/experimental alternative; verify
   component/weight licenses. The paper reports conflicting root/SR license
   text; root README alone cannot resolve component terms.
3. Triton-XDNA: experimental compiler/HSA research if measurements justify the
   added stack. Its XRT and HSA allocations are not interchangeable by assertion.

These are **research options**, not installed dependencies or authorized driver
changes. Keep Vitis while it can prove correct meaningful SESR placement/context
and useful complete-frame service. Missing newer telemetry ioctls alone does not
prove inference failure or justify replacing Valve's in-tree driver.

Verify actual PCI/APU, shipping SteamOS/kernel/config, driver binding/provenance,
readable firmware identity, caller and user-manager memlock, installed runtime
metadata and actual loaded compatibility. Passive metadata cannot answer every
one of these. Relocatable runtimes may not appear in a package database.

After genuine H1 and baseline H2, use the [capability-only importer plan](../hardware-gates-steamos.md#h4--capability-ladder-input-and-output-separately).
No buffer allocation/import, DMA-BUF plumbing or inference is part of that future
capability query. Provider/device inspection still needs its own owner review.

Then follow [graduated H3](../hardware-gates-steamos.md#h3--shared-apu-budget):
stable NPU alone, modest controlled Vulkan coexistence, representative game load.
Keep matched GPU-only controls and abort on incorrect/stale output, firmware
timeout, context/device loss, GPU disruption or predeclared thermal/timing limits.
No active test is executed by this amendment. A separate512 model comparison
and trained native3× evolution wait for measured baseline bottlenecks.
